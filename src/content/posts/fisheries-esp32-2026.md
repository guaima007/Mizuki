这是我参加第九届（2026 年）全国大学生嵌入式芯片与系统设计竞赛应用赛道乐鑫赛题时做的项目。参赛报告里的名字是《基于 ESP32-S3 的智慧渔养智能体图形交互系统》，工程里叫 Fisheries。

做这个项目时，我一直在想，如果小程序显示可以开循环水泵，但鱼缸旁边的浮球已经报了低水位，应该听谁的？最后我把这条规则直接放在了主控板上。后来加了语音和视觉，外部能提供的信息越来越多，水泵的最终控制权还是留在水箱边。

## 从一个小水箱出发

循环水养殖需要长期关注水里的溶氧和温度。做竞赛原型时，我们还用浮球判断循环水箱的水位是否足够。溶氧偏低时开气泵增氧，水位过低时锁住循环水泵，避免它在缺水时运行。

| 监测量 | 采集方式 | 系统怎么用 |
| --- | --- | --- |
| 水温 | DS18B20 数字传感器 | 温度显示、超限告警 |
| 溶解氧 | ADS1115 采集模拟电压 | 溶氧趋势、自动增氧 |
| 水位 | GPIO 读取浮球开关 | 水位状态、低水位停泵 |

2.8 英寸触摸屏用 LVGL 做了 DATA、CTRL、SET、LOG、SYS 五个页面。联调时我可以先在 DATA 页看传感器读数，再去 CTRL 页验证继电器动作，最后到 LOG 页找对应事件。只凭一张界面截图很难评价探头精度。图中的溶氧是原型按电压换算后的现场显示，实际养殖应用还需要按探头要求单独标定。

## 两块 ESP32-S3 怎么分工

主控一开始已经要同时处理传感器、屏幕和继电器。我先把麦克风接到独立的 ESP32-S3-Zero，后来迁到集成音频和摄像头接口的副板。麦克风移出主控后，两路继电器也从预留的 I/O 扩展方案改回 GPIO 直驱。联调时，采样和执行在水箱一侧可以独立检查，音视频则可以在 PC 上单独排查。

![系统架构图。左侧主控板读取水质传感器并控制继电器，中间 EMQX 连接小程序，右侧 PC 上位机接收副板音视频并通过串口连接 STM32 云台](/images/posts/fisheries-esp32-2026/architecture.webp)

*图 2 · 按参赛报告和后期联调文档重绘的系统架构。*

| 模块 | 放在这一层的工作 | 对外数据 |
| --- | --- | --- |
| ESP32-S3 主控 | 采样、触屏、<br>保护和执行 | 水质、告警、回执 |
| ESP32-S3 副板 | INMP441 采音<br>OV2640 拍摄<br>NS4168 播放 | PCM、JPEG、<br>播报音频 |
| PC 上位机 | YOLOv8 检测<br>DashScope／Qwen 交互 | 识别结果、诊断、<br>云台目标坐标 |
| STM32 控制器 | 双轴驱动、<br>零点、限位、急停 | 云台状态 |

摄像头的 JPEG 和麦克风的 PCM 直接进 PC 网关。MQTT 这边主要传水质、告警、识别结果和控制消息。后期演示还用 WakeNet 在板端做唤醒，检测到唤醒词后才打开短时音频上传窗口。上位机把视觉画面和服务日志放在不同页面，排查时可以先确认有没有收到图像，再看识别和后续动作。

## 一条开泵命令怎么走完

小程序的开关发出 `cmd`，里面带有请求编号、设备目标和开关意图。主控收到消息后调用 `app_core`，再把请求编号、处理结果、原因和泵状态放进 `cmd_ack`。若浮球已经报低水位，循环水泵会保持关闭，界面会收到低水位拒绝回执。这时 MQTT 通信正常，可以直接从回执定位到控制规则。

| MQTT 主题后缀 | 在界面里对应什么 |
| --- | --- |
| `state` | 水质、运行模式、泵状态 |
| `event` | 低水位、设备超时等事件 |
| `cmd` | 小程序或网关的控制请求 |
| `cmd_ack` | 请求编号、处理结果和原因 |
| `agent/history` | 网关生成的水质诊断摘要 |

![微信小程序里的水温、溶氧、水位和运行模式卡片，下方是气泵与循环水泵开关 w-55%](/images/posts/fisheries-esp32-2026/mini-program.webp "图 3 · 参赛报告中的微信小程序界面局部。")

### 自动增氧和低水位保护

固件给增氧气泵设了两条阈值。溶氧持续低于启动阈值才开泵，持续高过停止阈值才停泵。这样读数在临界点小幅波动时，继电器不会频繁切换。循环水泵走另外一条保护规则，运行中收到浮球低水位信号也会停泵。

| 联调场景 | 预期行为 |
| --- | --- |
| 自动模式、有效溶氧<br>低于 4.0 mg/L 达 5 秒 | 主控启动增氧气泵。 |
| 自动模式、有效溶氧<br>高于 5.5 mg/L 达 5 秒 | 主控停止增氧气泵。 |
| 浮球进入低水位 | 拒绝启动循环水泵，<br>运行中的循环水泵也会关断。 |
| ADS1115 采样无效 | 主控暂停自动增氧判断。 |
| 达到单次运行时限 | 对应泵关断并记录事件。<br>气泵 120 秒，水泵 300 秒。 |

表中的阈值来自后期演示版的固件默认配置。网关发现温度或溶氧采样无效时，会拦截它自己生成的开泵请求。现场验证低水位保护时，可以先将浮球置于低水位，再点小程序里的循环水泵开关，同时看实体继电器、回执和日志。即使远程请求送达，循环水泵也应保持关闭。

## 鱼类检测的数据和结果

视觉演示把鱼体目标按黑色、红白和黄色分成三类。训练流程先人工标一批图，用初版模型给后续样本预标注，再逐张检查类别和检测框。相邻鱼体或者遮挡场景里，一个预测框容易套住两个目标，这类样本尤其需要回看。

| 本地划分 | 图像数 | 黑色框 | 红白框 | 黄色框 |
| --- | ---: | ---: | ---: | ---: |
| 训练集 | 704 | 468 | 454 | 433 |
| 验证集 | 133 | 87 | 102 | 91 |

表里的数量按本地图像和同名 YOLO 标签统计。画面中的目标是水箱里的演示鱼模型，类别来自这次演示的颜色定义。

![参赛识别画面中，黑色、红白和黄色鱼模型分别标出检测框和置信度](/images/posts/fisheries-esp32-2026/fish-detection.webp)

*图 4 · 从参赛报告的 PC 识别截图截取的检测画面。图中分数是单帧框的置信度。*

我们训练了 YOLOv8s 基线，又试了一版带 SE 通道注意力的 YOLOv8s。SE 对特征通道重新加权，想看看鱼体轮廓和颜色在水面反光、背景杂乱时能否更容易被区分。两次训练都用了 640 像素输入尺寸、批大小 4 和 SGD。下面是原始训练日志的第 120 轮验证结果。

| 验证指标 | YOLOv8s | YOLOv8s + SE |

| Precision | 0.9532 | 0.9684 |
| Recall | 0.9419 | 0.9447 |
| mAP@0.50 | 0.9689 | 0.9717 |
| mAP@0.50:0.95 | 0.6113 | 0.6115 |

![两种模型从第 1 到第 120 轮的验证曲线对比，上图为 mAP@0.50，下图为 mAP@0.50:0.95](/images/posts/fisheries-esp32-2026/validation-curves.webp)

这组验证里，SE 版的 mAP@0.50 高约 0.28 个百分点。综合多个定位阈值的 mAP@0.50:0.95 基本持平。当前配置沿用验证集作为测试入口，尚缺一批按拍摄场次独立留出的测试数据。水面反光、不同水箱以及活鱼环境下的表现都需要另外验证。

## 识别框怎样变成云台动作

后来的演示版加了一套 STM32F103 双轴步进云台。此前检测框主要画在画面上，要用它驱动云台，PC 还得决定追踪哪一条鱼，把框中心转换成归一化坐标，再做平滑后送给 STM32。云台控制器根据位置误差和中心死区决定是否纠偏，目标在画面中心附近轻微抖动时，步进电机可以保持静止。

| 演示情况 | 对应行为 |
| --- | --- |
| 黄色鱼模型偏离中心 | PC 发送平滑后的框中心，<br>STM32 驱动双轴纠偏。 |
| 目标被遮挡 | 超过 800 毫秒无坐标便停止纠偏。<br>PC 丢失目标 1.5 秒后请求低速搜索。 |
| 手动接管或急停 | 手动操作退出自动追踪，<br>急停锁存并关闭电机输出。 |
| PC 推理不可用 | ESP-DL 降级方案保留鱼体存在性检测。<br>三类识别和坐标追踪依赖 PC。 |

这两条链路最后用了相似的设计。语音和小程序可以请求开泵，水位保护和泵超时由主控在本地执行。视觉模型可以给出目标坐标，云台控制器按机械限位和通信状态决定怎么动。调试时，只要能从回执和状态里看清是哪一层拦下动作，就容易知道接下来该查哪一段。
